# ift join: hosts with no app, ift serve, and the login step

What this covers: the windowless host (`headless.rs`) and `ift serve`, the app taking over from it, a Linux host's canvas built from its running sessions, `ift join` starting `ift serve` over ssh, and the login step before the viewer starts (fingerprint and password questions, the shared connection, the askpass dialog).

Read it before touching `infiniterm-core/src/headless.rs`, `infiniterm-cli/src/serve.rs`, `infiniterm-core/src/backend/ssh_login.rs`, the `ift askpass` verb in `infiniterm-cli/src/main.rs`, or the start of `main()` in `infiniterm-ui/src/main.rs`.

Related: `join-and-remote.md` (the host side and protocol), `join-viewer.md` (the viewer window and connection loss), `daemon-and-backends.md`.

A host with no window (#438, `infiniterm-core/src/headless.rs`): `Host::start` loads the canvas file, starts the daemon backend and the join server, and `Host::tick` does what the app's poll does without gpui, calling ONLY the model's own functions for every rule (`apply_pane_event`, `apply_hook`, `apply_remote_layout`, `record_published`, `save_text`, `sweep_stale`, `run_ift`, `tick`, the parking effects) so the app and the host cannot drift; the glue it adds is draining the channels, acknowledging bytes at once (no grid to parse them), the 500 ms save, `publish_layout`/`publish_agents`/`publish_config`, and starting or adopting a shell for a card with none (pty size from the rect with a nominal cell, `nominal_cells`). The module header lists what the app does on a tick that the host does not (no grid so no `ift read`, no window effects, no agent log, no take_ring, no orphan sweep).

`ift serve` (`infiniterm-cli/src/serve.rs`) is the process around it: foreground until SIGTERM/SIGINT, `--detach` (setsid, output in `serve.log`, returns when `j.sock` answers), `--stop` (SIGTERM, waits); `<data>/serve.pid` is written at start, and a pid file is believed only when `ps` says that pid's command line is `ift serve` (`headless::live_serve`), so a stale file never gets an unrelated process signalled. It refuses to start while anything holds `infiniterm.sock` (the app or another serve). A stop flushes the canvas, removes both sockets and leaves every session running.

The app's takeover: before anything else in `main()` it calls `headless::stop_running_serve` (SIGTERM to the pid in serve.pid, only when `live_serve` confirms it is an `ift serve`, waits 10 s): `Stopped` and the app goes on, loading the canvas serve just saved (same file) and adopting its sessions, and viewers rejoin through #442's retries; `Stuck` shows an osascript dialog (the app has no window yet) and exits, never silently.

A host with NO canvas (no file, or no cards) and running sessions builds one at start (`headless::seed_from_sessions`: one card per session, oldest first by its meta's `started`, in the meta's `cwd` or the home, keeping the session id so the first tick adopts it, placed by the model's block grid): that is how a Linux server, which never had an app, gets a canvas (#439); the same `ift serve` binary, no other Linux code.

`ift join` starts it (`remote::start_serve`, `ssh host ift serve --detach`) when the handshake fails with "no running infiniterm to join" (`remote::is_no_host_running`, the one failure answered that way; `--check` only reports it), then probes again; `INFINITERM_JOIN_NO_WINDOW=1` makes `ift join` stop before `open -n`, which is how tests run it.

The login step (#450, `backend/ssh_login.rs`): `ift join` probes the host with the viewer's own non-interactive ssh before anything else; a host never seen (`known_hosts`) or with no key, and a terminal, makes it run ONE plain `ssh <host> true` with the terminal's stdio so ssh asks its own questions, then probes again; a CHANGED host key is an error with the new fingerprint (`classify`, also used by `classify_join_failure`), never a question, and nothing passes `StrictHostKeyChecking=no`; no password is read, kept or logged by us. The ONE ssh it runs is also the master of a shared connection (`-M`, `ControlPath=/tmp/iftc-<uid>/<hash>`, short because ssh adds 17 characters to a 104-byte socket path, `ControlPersist=10m`): if the host then works with no question (keys) the master is stopped, since a shared connection stalls every card behind a flooding one; if it needs the password (`Login::Shared`) every ssh of the viewer gets `-o ControlPath=...` through `INFINITERM_JOIN_ARGS`, and the window's quit runs `stop_master` (`ssh -O exit`). With no terminal the same ssh runs with `SSH_ASKPASS` set to a small owner-only script (`write_askpass_helper`, next to the control socket, it holds only the path of `ift`) and `SSH_ASKPASS_REQUIRE=force`; ssh then calls `ift askpass <question>` (plumbing in main.rs), which shows an `osascript` dialog (the question is passed as `argv`, never spliced into the script; a hidden-answer field for a password, Yes/No with No the default for the fingerprint) and prints the answer for ssh alone, never to a file or the log. The dialog is `osascript`, not the app's own window: the viewer app does not exist yet at the login step.
