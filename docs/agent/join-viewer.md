# ift join: the viewer window

What this covers: the viewer side of `ift join <host>`: how the viewer edits its own copy of the host's canvas and how the host merges those edits, what stays per client, how terminals draw and connect, what happens when a connection is lost, and why settings and keybindings are the host's.

Read it before touching `infiniterm-cli/src/join.rs`, `infiniterm-core/src/backend/join_client.rs`, `remote.rs` (viewer paths), `Model::apply_snapshot` / `apply_remote_layout` in `model/persist.rs`, `terminal_body.rs`'s `LostLink`, `terminals.rs`'s viewer reconcile, or the `viewer` flag on `DaemonBackend`.

Related: `join-and-remote.md` (the host side and the wire protocol), `join-serve-and-login.md` (`ift serve`, hosts with no app, the login step), `daemon-and-backends.md`, `traps-code.md` (splicing sockets across threads).

- Join, the viewer side (#423, stage 2): `ift join <[user@]host>` gives FULL CONTROL of the infiniterm running on another Mac, as if sitting at it (Ekin: "like I'm sitting in front of the Mac mini"). It opens a SECOND app in viewer mode (`infiniterm-cli/src/join.rs`, reusing `connect.rs`'s parsing and `open -n`; `INFINITERM_JOIN=<host>`, folder `~/.infiniterm/joins/<host>`; `INFINITERM_REMOTE_NAME`/`_COLOR` give it the host chip) after asking the host once (`remote::probe_join`). `remote::classify_join_failure` is the rule for a failed handshake: only a real connection failure (ssh down, a timeout, a reset) retries; anything the host said, or its login refused, is fatal and said once with a sentence, because waiting will not change it (an `ift` too old answers a shell error where `ift-join <major> ...` should be, a refused major, no app running, a refused key). Protocol major 2 (a host that speaks 1 refuses a viewer asking for 2, so a viewer never believes it controls a host that would ignore it). HOW control works: the viewer edits ITS OWN copy of the canvas with the app's usual commands (every card command, Cmd+T, close, move, split, group, rename, workspaces, tidy), and when it changes (`write_layout`, the usual 500 ms debounce, `send_up`) it sends the whole layout UP to the host as a `U` canvas message naming the revision it edited (`{base, layout}`). The host applies it in place with `Model::apply_remote_layout`, through its OWN paths: a card missing from it is closed by the host's normal close (a terminal parks and ends as it always does), a terminal it has not seen becomes a normal new card (the host's reconcile starts the shell on the host; the viewer's card shows "starting on the host..." until the host's next snapshot carries its session, then adopts it), and rects, titles, groups, workspaces and their order follow. A new card from a viewer is only ever a terminal (an editor would name a path on the viewer's Mac); a number the viewer picked is replaced by the host's. The host then publishes the new canvas with a new revision (`L` then `V`, to every viewer, the sender too), which is how the viewer receives its card's session. An edit is MERGED, never refused for a busy host: the host keeps the last 32 canvases it published (`Model::published`, filled by `record_published` in `write_layout`), diffs the viewer's layout against the one at the edit's `base` revision, and applies only the fields that differ (a card's rect, title, group, a removed or added card, workspaces). What the host changed meanwhile stays; the same field changed by both goes to the viewer. A `base` the host no longer remembers is `Stale`: dropped, and the host republishes so the viewer resyncs. The old rule (stale when the host had an unpublished change) reverted a busy host's own work and dropped the viewer's edits. What stays per client: viewport, zoom, focus, selection, active workspace and each workspace's own viewport (the first snapshot sets them once, `Model::snapshot_seen`); a viewer is `read_only`, so `save_text` is `None` and nothing is written into its data dir. Cards that are not terminals are REAL cards in a viewer with no body (`reconcile_editors` and `reconcile_browsers` are skipped; `paint.rs` draws "<kind> on <host>"), so they move, group and close like any card and go back up whole, and no path on the viewer's Mac is read and shown as the host's. A viewer's terminal is DRAWN at the host's columns and rows (`TerminalBody::fixed_cells`, from the pane's size: the host's hello and every `Resize` it sends), because the shell wraps to the host's width; a card resized in the viewer is a move like any other, the host refits its pty and the new size comes down.

The viewer backend is the `viewer` flag on `DaemonBackend`, not a `Panes` variant, and it owns no session: a card closed in a viewer disconnects its pane (the host closes the card from the canvas that went up, parking and all), a card with no session is started by the host (so `spawn_now` here is refused: starting a shell on the viewer's Mac would be the wrong Mac), `kill_orphans` is a no-op (it owns none, so it must not kill the ones the host's directory might hold), and adoption goes through the host app's join socket (`remote::connect_join`, `ssh host ift proxy join session <id>`), never through the host's `iftd`, which serves one client and would drop the host's own window. Each has a control test on an ordinary backend (`viewer_tests` in `daemon.rs`).

Lost connections (#442): a viewer card's session connection ending without `Exited` is `PaneEvent::Detached` as ever, which sets `Card.displaced`; for a viewer `terminals.rs` runs a `LostLink` (`terminal_body.rs`: a banner naming the last failure, back-off 2 s doubling to 30 s, a final host answer such as "no session" stops it) and joins again through `DaemonBackend::begin_reconnect` on a thread (the handshake waits on ssh; `take_reconnected` registers the pane on the app's thread), the FIRST join of every card goes the same way (a blocking adopt held the frame, 38 times in a row), `CanvasEvent::Connected` (the canvas is back) makes every lost card try at once, and a key into one is refused with a notice. The canvas client (`run_canvas_client`) never treats a refusal as final once it has joined (the host app quitting answers "no running infiniterm"), and backs off to 30 s. A stalled connection is ended by ssh's own keepalive (15 s x 3), not by the viewer.

Settings and keybindings are the HOST's (#433): the host sends the text of `settings.json` (`S`) and `keybindings.json` (`K`) on the canvas stream before the layout and at every change (`JoinHub::publish_config`, fed by the app's config watcher and read once at start), and the viewer applies them in memory through `apply_settings_text` / `apply_keymap_text`, so validation and the keep-what-you-had rule are the usual ones; the viewer ignores its own config folder's changes, never writes a settings file (a `SaveSetting` in a viewer is a notice that the settings are the host's, the first step; sending the edit to the host's file is not built), and keeps the host chip colour (`remote` is set). Agent colours come from the `A` canvas messages (`Model::apply_agent_states`); a viewer skips the stale sweep (it would end a card the host still has working), the first-card seeding and its own join socket (the update check is already off for any instance with its own data dir, which `ift join` always sets), and the relay's tap is switched off (`Relay::set_enabled`) when `join.enabled` is off or the window is a viewer. A viewer can write to any session id the host holds and now edits the whole canvas: the same trust as `ift send`, and ssh is the only way in.

- A Cmd+click on a path in a joined terminal (#555) is a REQUEST to the host, never a card born in the viewer's copy of the canvas: the terminal's paths are the host's, so `TerminalBody::remote_paths` (set from `AppView::viewer`) skips the exists check on this Mac's disk (every path-like text is a link, `scan_links`), and a click returns `BodyAction::OpenOnHost` which `send_open_request` sends up as `O` `{card, cwd, path, line}` on the same uplink as the edits (`join_client::Uplink`, so they keep their order). The join server resolves it on ITS disk (`join::resolve_open`: `~` and relative to the card's cwd, file or folder) in the viewer's reader thread: not found is a `N` notice back to that one viewer only (shown as a status), found goes to the app (`JoinHub::take_opens`, `apply_remote_opens` in the app's poll and in `headless::Host`), which calls the model's own `open_in_card` beside the card clicked; the new editor or folder card then reaches every viewer through the next canvas publish like any card. Shift+click on a path does nothing in a viewer (the system's handler would look at this Mac's disk). Old viewers skip `N` and old hosts skip `O`: no protocol bump.

- A file or folder dropped on a joined terminal, or an image on the clipboard at Cmd+V (#556), is sent to the HOST first and the card gets the host's path: the program in the card runs there and cannot read this Mac's. `AppView::file_drop` (viewer and a terminal card) and `BodyAction::PasteImage` (`remote_paths` and a clipboard with an image and no text) call `send_to_host`, which on a thread copies each item over the ssh the viewer already uses (`backend/host_drop.rs`: a file through `cat`, a folder packed with `tar`, an image as `clipboard.<ext>`) into `$HOME/.infiniterm/drops/<id>/` on the host, one folder per drop, and the same ssh removes drop folders older than `KEEP_DAYS` (7); the poll's `drain_host_drops` then types the host paths POSIX-quoted into the card (the host's shell is assumed POSIX) or shows the failure. A drop on any other kind of card is unchanged. Ctrl+V is an agent's own paste chord and Claude Code reads the clipboard of the machine it runs on, which in a joined card is the HOST's, so it is decided here (`ctrl_v_sends_image`): this Mac's clipboard holding an image and NO text sends the image to the host and types its path INSTEAD of forwarding the key; text, or no image, forwards `^V` as ever.

- A viewer GOES TO the card its host opened for it (#565) and SEES the host's in-place editors (#566). After `send_open_request` the model remembers the card ids it had (`await_host_open`); the first snapshot (`apply_snapshot` -> `follow_host_open`) with a card not in that list focuses it and pans to it (the host does this in its own viewport; the viewer's is its own). It lapses after `OPEN_WAIT` (15 s) so a card the host's user opens later never pulls a viewer's focus. A cover (`ift <file>` in a terminal, `model/cover.rs`) is left out of the file but NOT out of what the host publishes (`publish_text`) or a viewer sends up (`layout_snapshot`): the card carries `coverOf` (the terminal id), `apply_snapshot` rebuilds `covers` from it, so the viewer lays and treats it as the host does and the host's merge sees it unchanged, not closed. A cover is closable from either side (#568): `apply_remote_layout` closes a card the viewer dropped, covers included, and the host's `close_card` answers the waiting `ift`; a guard that skipped covers there made the host keep the card and publish it again, so it came back after Cmd+W. `INFINITERM_KEYLOG` prints each file request's time (`[files] <host> <op> <path> ok|error N ms`, and `connect`) from `file_client.rs`.
