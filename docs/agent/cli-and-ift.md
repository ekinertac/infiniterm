# The ift command line and file drops

What this covers: what `ift` verbs do and how they behave: `ift <file>` editing in place over a terminal card, `ift send` / `read` / `close` / `run`, the output of `ift ls`, `ift sessions`, `ift commands` and `ift completion`, and what a file dropped from the Finder does.

Read it before touching `infiniterm-cli/src/main.rs`, `ift.rs`, `completion.rs`, `infiniterm-core/src/model/ift_in.rs`, `model/cover.rs`, `drop.rs`, `save_as.rs`, or the hook installers.

Related: `editor.md` (the editor card that covers a terminal), `daemon-and-backends.md` (`ift attach`, `ift sessions`), `join-and-remote.md` (`ift connect`, `ift proxy`), `traps-workflow.md` (`ift send` text and Claude Code's paste).

- `ift <file>` run INSIDE a terminal card edits in place, the way `vim` would (2026-09-26, `model/cover.rs`): the app's `edit` verb opens the file in an editor card laid exactly over that terminal, born locked (`EditorTabs::locked` starts from `card.locked` in `reconcile_editors`, since the lock is otherwise the body's), and answers the request only when that card closes (`Model::edit_waiters`, `Effect::CliReply`, `reply_deferred` tells the ui not to answer now), so `ift` blocks like vim and `EDITOR=ift` works for `git commit`; `CliState::dispatch` waits with no timeout for `edit` alone, and the client reads with none. The cover is an ordinary editor card (lock, Cmd+S, the unsaved guard, drafts all its own); the pairing is session-only (`Model::covers`), a cover is never saved (a relaunch ends the waiting connection) and the save writes the terminal as focused instead; the covered terminal is out of `here()` so navigation, tidy and fit-all see one card; the drag's overlap checks let the pair share a rect (`paired`); `sync_covers` in `tick` moves whichever of the two did not move; closing a cover is `:wq`, no reopen ring, no undo step, focus back to the terminal. `ift -n <file>` is the old behaviour, a card of its own, returning at once; a directory, or `edit` from outside a terminal card, opens a card as before. A path that does not exist is a NEW file, vim's way: any argument that is not one of ift's verbs is a path (a typo'd verb opens an empty editor, chosen over a "has a dot or a slash" rule because that would be one more hidden thing), `ift` refuses a missing directory up front (`resolve` in the cli; vim finds out at the first write), and `EditorBody::load` opens a missing file empty with a "new file" notice so the first save creates it and a close without one leaves nothing. An untitled buffer's first save (`open_save_as`, `save_as.rs`) opens the save-as field on the card's directory and `untitled.txt` with only the stem selected (`Prompt::select`, `Field::open_selecting`), the macOS panel's shape in our own dialog; a missing directory returns to the field with the text kept, an existing file asks "Replace" first, and the close sheet's Save on an untitled buffer runs this and then closes.
- A file dropped from the Finder does what the thing under the pointer IS (`drop.rs`): a terminal gets the shell-escaped path as a paste, because a terminal is a terminal and the drop has to work mid-command; a browser goes to the file; everything else opens a card through `open_plan`, the same decision `ift <path>` reaches by typing. `shell_quote` is the whole security story: a file called `; rm -rf ~` reaches the prompt as text.
- `ift send <card> <text|--key K> [--enter]`, `ift read <card>`, `ift close <card>` and `ift run <cmd>` drive cards from a script (`ift.rs` parses, `model/ift_in.rs` runs, `Grid::text` is what read returns); `ift ls --agents` adds the agent column. Cards are named by number or id (`parse_card_ref`). `ift read <card> --ansi` (#713, 2026-11-10) answers with the screen's colours for a viewer that is not a terminal (the phone app's canvas draws a card's screen from it; joining every card's session for a preview would replay each history and hold a connection per card): `Frame::ansi`, one line per painted row, every run opened by ONE SGR sequence that resets and sets all of its own attributes with the resolved 24-bit colours, so a reader needs no palette and can cut a line anywhere. It is built from the body's `Frame`, not from the grid, because the resolved colours live there; `TerminalBody::ansi_text` brings that frame up to date the way a paint does (`update_frame` then `refresh_links`), since `update_frame` takes the grid's damage and a paint after it would skip those rows. The painted rows are the ones in view, so `--ansi` with `--all` is refused in `parse_read`, and a card scrolled up answers with what it shows. An `ift` from before the flag answers `unknown option --ansi`, which a caller can take as "plain text only".
- `ift ls` and `ift sessions` print a padded table with a header on a terminal and tab-separated rows without one into a pipe (`is_terminal`), so `cut -f1` keeps working; on a terminal `ift sessions` is two columns, the card number and the label (else the directory), because the full table did not fit a phone over ssh (Termius), and `--full` is every column; a pipe always gets every column. `ift commands` lists every registered command as id, label, key from the running app (the palette's list as text; `keybindings.default.json` has only the bound ones). `ift completion zsh` prints `_ift` (completion.rs, held to `SUBCOMMANDS` by a test) and `ift install` writes it to `~/.local/share/zsh/site-functions/_ift`, naming the fpath line when that directory is not on `$FPATH`; `ift omni` is sections, not columns, and stays as it is. `ift sessions` reads the save file for the card number and label per session, and `ift attach 7` resolves a number to the session that card holds now. `ift push add|remove|list` (`push_cmd.rs`, #649) edits the `push-devices` file and never talks to the app, so it works with infiniterm not running; see `settings-and-config.md`.
- `ift focus <card>` (#552, for a Raycast "Go to Card"): the number (`7`, `#7`) or id, resolved by `resolve_card_ref` like `close`, then `Model::go_to_card`, the palette's own path (show the card's workspace, focus, push `canvas.zoom.fitCard`), so the result is the same however you got there. Unknown card: `no card <arg>` and nothing changes; no argument: `focus takes a card`. It needs a running app and does not start it, and it does not bring the window in front of other apps (bare `ift` does, `open -b`); a launcher runs both.
- `ift workspaces` and `ift terminal --workspace <id|name|new> [--name T] [--] <dir>...` (#550, for a Raycast launcher): the workspaces are listed in tab order as id, name, cards, active (`*` or `-`, the `EMPTY` placeholder so a shell `read` keeps its columns; `format_workspace_list` strips tabs and newlines from a name). The flags are parsed in the APP (`parse_terminal_args`, `resolve_workspace` in `ift.rs`, the `terminal` arm of `ift_in.rs`), not in the cli, which only resolves the directories and passes the flags through, so the Finder service and a script see one behaviour. Resolution order is exact id, exact name (case sensitive; two matches is an error telling you to use the id), then the word `new`; a workspace actually named "new" is reached by its id. Everything, directories included, is checked before the first workspace or card is made, so an error leaves nothing behind (a `new` workspace for a folder that does not exist would stay empty). A chosen workspace is shown before the cards open, because "on the workspace on screen" stays the one rule of `open_terminal_at`. Flags only lead the directories and `--` ends them; an unknown `--x` stays a directory, as it was before the flags. `--name` without `--workspace new` is an error. No flags: unchanged.
- Finder service not showing (#344, 2026-11-06): `tools/bundle.sh` writes the `NSServices` entry, and `pbs -dump_pboard` listed it while Finder's right-click menu did not. The Finder services that DO show on the dev Mac (Automator workflows in `~/Library/Services`: Open in Cursor, iTerm2, VSCode) all carry `NSRequiredContext` = `{NSApplicationIdentifier: com.apple.finder}`; ours had none, so the entry now has it (`NSSendFileTypes` stays `public.folder`; theirs is `public.item`, which would also offer the item on files that the service then drops). NOT confirmed in Finder when written. If it still hides, try `public.item`, then `/System/Library/CoreServices/pbs -update`, then Finder > Services > Services Settings. A workspace submenu is not possible: a service is one static menu item. The Raycast extension (tarikkavaz/raycast-infiniterm) is the workspace picker, over `ift workspaces` and `ift terminal --workspace`.
- `ift phone add|list|remove`, `ift phone-gate`, `ift read --stream`, `ift settings show`, `ift snippets --nul` (2026-11-10, Ekin: QR pairing, printed in the terminal): the iPhone app is an ssh client of the Mac's own sshd, and `phone add` replaces pasting a private key. Pure logic is `infiniterm-core/src/phone.rs` (authorized_keys line editing, the pairing URL `infiniterm://pair?v=1&n&h&p&u&hk&k&d&i&iv`, reading the seed out of an OpenSSH key file so `ssh-keygen` makes the key and no crypto crate is needed, `tokenize` and `gate_args`); processes and files are `infiniterm-cli/src/phone_cmd.rs`. The line is `restrict,port-forwarding,permitopen=...x3,command="<abs ift> phone-gate"` with the comment `infiniterm-phone:<name>`: `remove` deletes only the line with exactly that comment. `phone-gate` splits `$SSH_ORIGINAL_COMMAND` itself (plain words of `[A-Za-z0-9_-./@%+=:,~]` and single-quoted words; a backslash, `$`, `;`, double quote is refused, so a path with a quote in it cannot be paired), requires the first word to be this binary's canonical path, allows only the table in `gate_args` (which includes `proxy files --read-only`, the file service that refuses `write` and `put_drop`, 2026-11-11; see `join-file-service.md`), and runs this same binary, never a shell. The QR holds the private seed and is printed to the terminal on purpose: the card's iftd buffer keeps it, and the command says so. The three stream verbs print exactly the bytes the phone's old shell commands printed (0x1e number 0x1f screen 0x1d; settings.json unchanged; `./name` NUL bytes NUL), so the app's parsers did not change. Not on Windows. `ift phone add` never touches a file outside `~/.ssh/authorized_keys` (and, with Tailscale SSH, the `phone-forward` marker in the config folder); `HOME=/tmp/x ift phone add n` tests it against a scratch home.

Tailscale SSH (2026-11-11): with `RunSSH` on (`tailscale debug prefs`), tailscaled answers on port 22 of the tailnet address with its own ssh server (banner `SSH-2.0-Tailscale`), which ignores `authorized_keys` (so `phone-gate` and the key's limits never apply) and may wait for a policy `check` login an app cannot show. Found on ekin-mini: the phone stalled 20 s on every connect. `ssh_port_for_phone` therefore runs `tailscale serve --bg --tcp=<port> tcp://localhost:22` (first free port from 2222, or the existing forward to :22, read with `phone::plan_forward` from `tailscale serve status --json`) and puts the port in the QR (`p=`). That port reaches the normal sshd, which reads `authorized_keys`: checked from the MacBook with a restricted key (allowed verbs run, `ls` refused, `proxy join canvas` works, the host key is the pinned one). It needs the user to be the Tailscale operator. The cost is said in the command's output: sshd here allows password and keyboard-interactive login, reachable from the tailnet on that port. `phone add` writes the port to `<config>/phone-forward` only when it made the forward; `phone remove` of the last phone runs `tailscale serve --tcp=<port> off` and deletes the marker, so a forward somebody else made is never closed. `--port <n>` skips all of it. The tests (`tests/phone_tailscale.rs`) put a fake `tailscale` first on PATH and a scratch HOME and config folder.
