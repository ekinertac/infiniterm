# Agents and card state

What this covers: the four card states and their colours, the workspace tab dots, the card label, state that comes from any program (OSC marks) and not only from agent hooks, the adapters for Pi, OpenCode, Codex, Antigravity and Cursor, `agent.log` and `usage.log`.

Read it before touching `infiniterm-core/src/agent_state.rs`, `program_state.rs`, `shell_integration.rs`, `usage_log.rs`, the hook binary `infiniterm-hook`, `infiniterm-cli/adapters/`, or anything that colours a card, a tab or a frame.

Related: `terminal.md` (the zsh command line), `daemon-and-backends.md` (a parked card's hooks), `traps-code.md` (late `Notification` echoes).

Moved here from CLAUDE.md on 2026-10-19 with the text unchanged.

- Four card states, because `Notification` and `Stop` answer different questions: working (mid-turn, or a long command running; violet), waiting (blocked on you: a permission prompt, a question; yellow), failed (a non-zero exit, a `StopFailure`, OSC 9;4;2; red) and done (the turn finished; green). They get four HUES, not brightnesses, because two oranges are one colour at 40% zoom; failed was split from waiting on 2026-09-25 (Ekin: asking and broken are different news), and working left Claude's clay for violet the same day because clay and red blur at fit-all and blue is the selection ring's. A group frame carries NO agent state: it holds several sessions and one colour cannot say which of them wants you, so colouring it drew the eye to the box instead of the card that was asking. The tabs reorder by dragging one onto another (`tab_drag.rs`: gpui's `on_drag` / `drag_over` / `on_drop`; the drop takes the target tab's index through `Model::move_workspace`, `workspaces::reordered` is the pure part) and from the palette (`workspace.reorder.left` / `.right`, no keys), 2026-10-06, #242; the order is the saved one. The workspace tab wears ONE DOT PER CARD in the cards' reading order on the canvas, top row first, left to right (`workspaces::reading_order`, then `tab_dots`), grey for a card with nothing to say and the card's own hue otherwise, a row of lamps that light one at a time. Done means UNSEEN (2026-09-27, `Model::clear_seen_done`): the focused done card goes grey once watched `SEEN_MS` (the switcher's 1.5 s dwell, so walking past is not reading) with the app in front, or at once when typed into; before, a Done card stayed Done until its next turn, the tab lit only turns finished after you left the workspace (`left_at`, removed), and Ekin had seven green cards and no green dots, which said nothing. Nothing else in the chrome may borrow an agent colour; `warn` exists for that. A card's title is a name somebody chose; the label derives name, else the agent's session name (its terminal title, trusted only on a card that `runs_agent`: a transcript this session or a saved `agentSession`, and saved itself as `agentTitle` since 2026-09-25, because after a relaunch an idle Claude card had neither the transcript nor the title in its ring and was labelled by its directory), else process, else directory.
- A card's state also comes from ANY program, not only an agent's hooks (2026-09-24, `program_state.rs`): the model scans each card's LIVE output (`PaneEvent::Output`, never `Replay`, or old marks relight cards) for OSC 133 (133;C a command started, 133;D;<status> it ended), OSC 9;4 progress (1/3 working, 2/4 waiting, 0 done) and OSC 9 / 777 / 99 notifications (waiting). A command that runs `LONG_MS` (5 s) shows working and ends done on status 0, so an `ls` never leaves the card green (green on every shell card would say nothing); a FAILURE shows failed however quick it was (Ekin, 2026-09-25), except Ctrl+C's 130; the next command clears the last result; a full-screen program (the alternate screen: vim, htop) never colours it; a hook during the command, or an agent session on the card, leaves the hooks in charge; and the stale sweep skips a running command, a quiet build is not a crashed agent. zsh sends no marks itself: `shell_integration.rs` writes a `.zshenv` shim and `infiniterm.zsh` to `<data>/shell/zsh` at launch and a shell card's zsh starts with ZDOTDIR there (the user's own ZDOTDIR handed over as `INFINITERM_ZDOTDIR`); the shim puts ZDOTDIR back and reads the user's files, the way Ghostty and VS Code load theirs. Only zsh, and only shells started after the update: an adopted daemon session keeps the shell it had. Every mark goes to `agent.log` as a `[shell]` line, a command's end with how long it ran (before cb280fd they went to the debug stream, and a failure that showed nothing left no trace).
- `usage.log` beside the save file (`usage_log.rs`, 2026-09-27) gets a line for every command the registry runs (key, palette or `ift`, from the registry's log hook in `runtime.rs`) and every finished mouse gesture (`AppView::note_use`: a card dragged, a group dragged, a resize, a pan, a wheel zoom at most once per `ZOOM_GESTURE_GAP_MS`, the double-click and chord fits); `ift usage [days]` lists what was used and every command and gesture that was not, against the live registry. Local only, capped at `MAX_BYTES`; it answers Ekin's "what features did we add that I do not use", and it is why the README's no-telemetry line still holds.
- Agents other than Claude Code report through adapters that speak Claude's hook vocabulary (`agent_state::apply_hook_event` maps event NAMES): Pi's extension (`infiniterm-cli/adapters/pi.ts`), OpenCode's plugin (`adapters/opencode.js`, `ift install-opencode-hooks`, #25: `session.status` busy, tools, `permission.asked`/`question.asked` as `PermissionRequest`, `session.error` as `StopFailure` except an Esc's `MessageAbortedError`, the `session.idle` after a failure swallowed so failed stays failed, sub-agent sessions with a `parentID` left out; one export only, since OpenCode calls every export as a plugin; no transcript, OpenCode keeps sessions in SQLite), and Codex's own hooks (0.145+, `~/.codex/hooks.json`, `ift install-codex-hooks`, #26) whose event names are Claude's plus `PermissionRequest` (waiting, whenever it comes). The hook binary takes the agent's name after the event (`infiniterm-hook Stop codex`), which lands on `Card::agent_kind` (saved `agentKind`) and picks a lost session's resume command (`agent_state::resume_command`: `codex resume <id>`, `opencode --session <id>`; none for Pi). Antigravity (`agy`, #300, 2026-10-11): `ift install-antigravity-hooks` writes `~/.gemini/hooks/infiniterm-antigravity-hook.sh` and a hook named `infiniterm` in `~/.gemini/config/hooks.json` (`antigravity_hooks.rs`; PreInvocation, PreToolUse, PostToolUse, Stop; the event name is the script's `$1` because the stdin JSON has none); `Stop` counts only with `fullyIdle` true, a non-empty `error` or an error reason is `StopFailure`; no event for a permission prompt, so no waiting state; resume is `agy --conversation <id>`; the adapter prints nothing, because PreToolUse's documented `decision` could override the user's permissions. The Cursor and Antigravity scripts are python under a shell heredoc: python's stdin is the script, so the shell reads the piped JSON into `IFT_HOOK_INPUT`, and `subprocess.run(input=...)` needs `text=True`; the Cursor script did neither until 2026-10-11 and never reported anything (`run_adapter` in the cli tests runs the real scripts). Codex gaps: no failure hook (an errored turn never reaches `Stop`, so the card stays working until the stale sweep), no hook for its questions, hooks need a one-time `/hooks` approval in Codex, and its rollout file is not Claude's transcript format.
- Every agent state change is appended to `agent.log` beside the save file (time, card, hook event, transition; capped at 512 KiB). It is the first thing to read when a card's colour looks wrong. A `Notification` flips a card to waiting only from working: one that arrives after `Stop` is a late echo, not a question.
