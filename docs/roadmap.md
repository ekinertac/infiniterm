## v2: what survives what

The daemon keeps a shell alive across the app quitting. Nothing keeps a process alive across a reboot, and Ekin does not want that; he wanted the scrollback, and since 2026-09-18 he has it (see Done).

- **Remote instances** (`ift connect <host>`, #118), widened 2026-10-03 from the remote canvas below. `ift connect root@100.1.1.1` opens a SECOND infiniterm app beside the local one: its own process, window, Dock icon and canvas, nothing shared. Two kinds of host with one launcher. A host with no app (a Linux server): the instance owns a canvas saved here per host, each terminal card is a shell kept by `iftd` on the server, and connecting again reattaches every card. A Mac that runs infiniterm (the mini, from the Air) is the same case: its bundle already has `iftd` and `ift`, so the instance gets its own canvas of shells on the mini, and the mini's own app and canvas are not touched (attaching a session displaces the mini's view of that one card until it lets go). Decided 2026-10-03: the canvas is persistent per host, settings are separate per host (seeded from the local ones once), browser cards are off in a remote instance (browsing through the server like a VPN is a later stage), and each host has its own colour on the title bar and the Dock icon, hashed from its name unless `--color` says otherwise. STAGE A STANDS (2026-10-04, #140 to #147): `ift proxy session` (the server half), the remote backend (`INFINITERM_REMOTE`, `DaemonBackend::new_remote`, spawn and adopt over ssh, `ssh host ift sessions` for the live list), `ift connect` (the check, a folder per host under `remotes/`, settings seeded once, `open -n`), the look (hashed colour, title chip, badged Dock icon, no browser cards) and the Linux packages attached to a published release. Checked with a stand-in ssh that runs the real proxy and daemon, in the real app (`tools/drive/connect.sh`, `remote.sh`) and in the Dock. FIRST REAL RUN (2026-10-04, a small Ubuntu 24.10 VPS as root, static x86_64 build from CI): the check passed and `iftd` and `ift` run there; the window opened and found a path-length bug (a 106-byte socket path, fixed by short folders, #150); the session itself over real ssh is the next thing to see. NOT done: a full run against a real server over real ssh; installing `ift` and `iftd` on a host (it only checks and says what is missing); a version check between the app and the host; the first release that attaches the Linux packages (the upload step has not run yet). Original plan: needs Linux builds of `iftd`, `ift` and the hook (static musl, x86_64 and aarch64; built by `.github/workflows/linux.yml` since 2026-10-03, #122: all three compile with no code change, about 1 MB each, and the core, term and session tests, the daemon's included, pass on Linux), `ift proxy` over ssh, a remote `Panes` backend, a per-instance Dock icon (`setApplicationIconImage`, untried) and a remote install with a version check. Stages: A terminals (a few days), B agent hooks over the connection, C remote files for editor and diff cards. Windows hosts come after: there is no `iftd` on Windows (ConPTY).
- **Remote canvas** (`ift connect mini`), SUPERSEDED 2026-10-03 by the remote instances above (Ekin: the new idea covers it); the live-replica viewer is not planned. Kept for the record: a viewer window on the Air showing the mini's live canvas, keys running on the mini, the way `wezterm connect` served 15 days of vacation work. Spec written and agreed 2026-09-22, docs/superpowers/specs/2026-09-22-remote-canvas-design.md: the host's app is the only authority, the viewer is a replica of the save file over the app socket, bytes come from each card's iftd as a droppable viewer client, transport is ssh with `ift proxy`. Terminals only in the first slice. About 3 to 4 days; start with `ift proxy` and the iftd viewer class, both testable headless.
- **Card state for any program, not only agents**: SHIPPED 2026-09-24 as designed (OSC 133 through a ZDOTDIR zsh shim, OSC 9;4 progress, OSC 9/777/99 notifications, 5 s before a command colours its card), plus one rule found while building it: a full-screen program (vim, htop, less) never colours its card. zsh only; bash and fish when missed. See CLAUDE.md.
- **The editor's own palette, Sublime's model** (designed 2026-09-24, not built). Cmd+P (free) inside an editor you are in: Go to File, every file under the tab's tree root fuzzy-matched on its path, from `git ls-files` in a repo (fast, skips ignored files) else a capped walk (~20,000), Enter opens a tab as the tree's Enter does. Cmd+Shift+P inside an editor: the same palette with an Editor section first, `Syntax: <language>` for the 17 grammars plus Plain Text, then the editor's actions, then the app's commands; one palette that knows where you are rather than two. The syntax choice is per tab and saved with the card. Half a day to a day.
- **Ring compaction**, only if 4 MiB proves shallow for a Claude card. Ink repaints are large and repetitive. The upgrade is to parse what is about to fall out of the ring into a headless grid with our own parser and serialise it back as the new front. Named in the daemon spec, deliberately not built.

## Open from the daemon work

- `tools/drive/daemon.sh` passed in full 2026-09-23 on the current build, pixels included: the synthetic redraw is one clean pair of lines before the quit (top 10) and after the relaunch (top 46, the loop kept running under `iftd` with no app attached), the adopted shell takes input, and Claude Code's screen after a quit and relaunch is row for row the one before it, nothing merged. The question the daemon design existed to answer is answered on screen. The old note that screenshots 01 to 04 "did not write" was the driver's own bug: every relaunch's `drive_start` cleared `$SHOTS`; the scenario sets `KEEP_SHOTS=1` after its first start now.
- What N daemons cost in practice, measured 2026-09-22 on the real canvas: 17 alive, 120 MB RSS total, 13 idle ones at 0.4 to 1.2 MB each, the busy ones 3, 8, 15, 23 and 65 MB. Idle is cheaper than the spec's ~2 MB guess; the 65 MB one is not explained by a 4 MiB ring and is worth a look if it grows (the ring's `Vec` growth, or the snapshot copy every 2 s, are the suspects).
- Colour reporting under tmux, Nerd Font glyph widths, a very long scrollback on adopt: the tmux handover's open items 2, 3 and 6, still true of tmux, mostly moot under the daemon.
